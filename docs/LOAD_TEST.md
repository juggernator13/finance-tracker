# Нагрузочный тест

Нагрузочный тест проверяет, как сервис отчётов справляется с одновременными запросами от многих пользователей через Gateway.

## Окружение

| Параметр | Значение |
|---|---|
| Инструмент | k6 |
| Среда | Docker Compose (все сервисы в контейнерах, сборка Release) |
| Точка входа | Gateway, `http://localhost:5000` |
| Компьютер | AMD Ryzen 5 7500f, 32 ГБ DDR5 5200 МГц, ОС Windows 11 Pro 26H2 64-bit |
| Тестируемый запрос | `GET /api/reports/by-category?year=2026&month=10` |
| Данные | один пользователь, загружены `bank1.csv` и `bank2.csv` |

## Сценарий

Файл: `tests/load/report.js`.

1. Один раз выполняется вход, токен используется всеми виртуальными пользователями.
2. Нагрузка растёт с 0 до 50 виртуальных пользователей за 10 секунд, держится 30 секунд и снижается за 5 секунд (всего около 45 секунд).
3. Каждый пользователь запрашивает отчёт по категориям и делает паузу 0,1 секунды.

Пороги прохождения:

- доля ошибок `http_req_failed` меньше 1%;
- 95-й процентиль времени ответа `http_req_duration` меньше 500 мс.

Запуск:

```
k6 run -e GW=http://localhost:5000 -e USER_EMAIL=<email> -e USER_PASSWORD=<пароль> --summary-export=tests/load/baseline.json tests/load/report.js
```

## Сравнение

| Версия | RPS | p(95), мс | Ошибки |
|---|---|---|---|
| Без кэша | 402,7 | 5,23 | 0% |
| С Redis | 405,0 | 5,03 | 0% |

## Выводы

- Сервис отчётов выдерживает 50 одновременных пользователей без ошибок: оба порога выполнены с большим запасом (p(95) = 5,23 мс при пороге 500 мс).
- Значение RPS ограничено самим сценарием: у каждого виртуального пользователя есть пауза 0,1 с, поэтому при 50 пользователях теоретический предел около 500 запросов в секунду. Полученные 402,7 RPS близки к этому пределу, то есть сервер не был насыщен.
- Максимальное время ответа 310 мс связано с единичными запросами в начале теста (прогрев соединений и сервисов), на 95-й процентиль это не влияет.
- Отчёт строится на небольшом объёме данных (несколько операций), поэтому разница между запросом к базе и ответом из кэша при такой нагрузке может быть небольшой. Для более заметного сравнения можно увеличить число пользователей или убрать паузу.
- Влияние Redis в этом сценарии незначительно. С кэшем RPS 405,0 против 402,7, p(95) 5,03 мс против 5,23 мс, среднее время 2,53 мс против 2,49 мс. Такие различия лежат в пределах погрешности замера, поэтому утверждать, что кэш ускорил ответы, нельзя.

## Ограничения теста

- Тестируется только чтение отчёта, импорт выписок и запись не нагружались.
- Нагрузка создаётся с того же компьютера, где запущены сервисы, поэтому результаты зависят от его ресурсов.
- Все запросы выполняются от одного пользователя и по одному и тому же месяцу.
